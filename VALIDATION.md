# VALIDATION.md

Instructions for an independent audit of this repository's implementation against the frozen protocol. The audit is run by a fresh Claude Code session (the validator) that has never seen the implementation session's context. Its job is to find disagreements between what PROTOCOL.md says and what the code does, and to establish that the reported numbers can be reproduced independently. It is not the implementer, and it does not fix anything. This document is fixed at validator launch; after launch it changes only in response to ambiguities the validator itself discovers, recorded as dated notes at the bottom, so the audit does not become a moving target.

## Ground rules for the validator

1. Read CLAUDE.md, PLAN.md, FREEZE.md, PROTOCOL.md, and AMENDMENTS.md first. PROTOCOL.md as amended by AMENDMENTS.md is the referee; where the two differ, AMENDMENTS.md controls. AMENDMENTS.md holds only post-freeze changes, so a header with no entries means the protocol stands exactly as frozen; passages in PROTOCOL.md marked "Adopted before the freeze commit" are protocol text settled during formation, not amendments, and the dated record of how each was reached is in the git history the freeze commit closes. Where code and protocol disagree, the disagreement is a finding; do not decide who is right.
2. src/ and tests/ are read-only for this audit. All validator code goes under validation/, all mutated copies under validation/mutants/. Never edit, fix, or improve the implementation, even for obvious bugs. Findings go in the report.
3. Write VALIDATION_REPORT.md as you go. Every check gets: check id, what was verified, the exact command run, the evidence (output snippet or file/line reference), and a severity: blocker, major, minor, or note. Blockers halt Phase 4 until resolved.
4. Independent means independent. Where these instructions say to re-derive something, write the re-derivation from the PROTOCOL.md text alone, without importing the corresponding lot module. Importing lot code to check lot code only proves the code agrees with itself. Loading cached data (features, manifests, parquet) through lot readers is allowed; recomputing the quantity under test through lot math is not.
5. Ambiguity is a finding. If the protocol underdetermines something the code had to decide, record the decision the code made and mark it "protocol gap, minor" so it can later be recorded in AMENDMENTS.md; PROTOCOL.md itself is frozen and is never edited.

Prerequisite before the audit starts: at kickoff, record the git commit hash for each normative artifact, PROTOCOL.md, AMENDMENTS.md, configs/analysis.yaml, and VALIDATION.md, and record whether the working tree is dirty. A missing, uncommitted, or dirty normative artifact is the first blocker: an audit against a target that can drift mid-run proves nothing. Every evidence entry in the report cites that recorded commit.

The validator's first action is to verify the four normative files against the sha256 values recorded in FREEZE.md, which also names the freeze commit and the Stream D closure commits that precede it. A mismatch is a blocker before any other work begins. The freeze commit is the normative boundary: everything before it is protocol formation and repair, everything after it is execution against frozen rules.

Kickoff also records content hashes of the data artifacts the audit depends on, because those are untracked and a commit hash says nothing about them. This closes a gap the earlier audit found and could not close: VALIDATION.md did not say where evaluation artifacts reside or how to pin ones that git does not track, so an audit could be reproducible in its code and unpinned in its inputs. The artifacts are the rendered scenes under data/, the frozen feature cache under cache/, and the evaluation outputs under outputs/.

Hashes are computed canonically so the validator can reproduce every one independently. For the feature cache, either the sha256 of a manifest that itself records each cached object's sha256, or a deterministic aggregate hash over the files. In both cases files are visited in sorted-path order, paths are relative to the repository root, and the ordering rule is recorded in the kickoff note alongside the hashes. The manifest set is hashed under the same sorted-path canonical ordering. Any other ordering produces a different aggregate and is therefore not a reproduction.

The validator's first dated note records this artifact-location gap and states that the kickoff content hashes are its resolution.

## Part 1: Static conformance audit

Read the code against the protocol. For each item, cite file and line in the report.

1.1 Pose convention. Poses stored as T_world_from_camera; the relative transform T_target_from_context = inv(T_world_from_target) @ T_world_from_context is defined in exactly one function. Grep for any second inline implementation of a relative transform or a matrix inversion of a pose outside that function; a duplicate is a major finding.

1.2 Rotation angle. Geodesic formula arccos of (trace(R) minus 1)/2 with the argument clamped to [-1, 1], stored in degrees, computed from T_target_from_context. Missing clamp is a major finding.

1.3 Pixel-to-patch mapping. The mapping pixel (u, v) to patch ((u + 0.5)/14 - 0.5) is defined once; bilinear sampling uses it; no align_corners=True anywhere in feature sampling. Grep for a second copy of the mapping constant; duplicates are major.

1.4 Transport. Splatting happens at pixel resolution carrying each pixel's patch feature; the z-buffer resolves occlusion at pixel level before pooling to the patch grid; coverage is the supported-pixel fraction per target patch; disoccluded locations are left empty, never zero-filled and scored.

1.5 Nulls. All three prediction nulls read from the context feature map. No-Warp-Copy reads at the same image coordinate as the target location. Neighbor-Patch reads one patch away from the correct correspondence location and is then transported like Oracle-Transport; verify this against the frozen definition in PROTOCOL.md, and if the code implements the other reading (one patch from the same image coordinate), that is a blocker because published orderings depend on it. Random-Patch is drawn within the context image, never across scenes.

1.6 Masks. Visibility buckets are computed from ground-truth depth of both views using the co-visibility depth tolerance from the normative analysis config; verify the code reads it from the config rather than hard-coding it. Grep the visibility module for any code path that touches estimated depth; any hit is a blocker.

1.7 Metrics. Raw cosine and centered cosine are both computed; record precisely what "centered" subtracts (global dataset mean or per-scene mean) and check it against PROTOCOL.md; margins over floors are computed at analysis time, not baked into rows.

1.8 Schema. Evaluation rows are long format with columns for variant, path, continuous rotation_deg, and continuous parallax; no bin labels in rows; bin edges live only in a committed config; the per-pair parallax statistic in code matches the protocol's definition (median per-point baseline over depth across the pair's co-visible set).

1.9 Encoders. DINOv2 preprocessing matches the official normalization and resize; models are in eval mode under no_grad; the VGGT wrapper builds a length-one sequence axis; the single-frame and batch-equality tests exist in the suite and are not skipped silently on the cluster.

1.10 Reproducibility. Every entrypoint sets seeds from config; configs for the completed runs are committed; outputs are never overwritten.

## Part 2: Independent numerical re-derivation

2.1 Geometry cross-check. Pick three pairs at random from the manifests, one per regime. From the protocol text alone, write a numpy reprojection: unproject 20 random pixels with ground-truth depth, transform, project. Compare against the pipeline's correspondences for the same pixels. Agreement must be within 0.1 pixel. Any systematic offset (a constant half-pixel, a flipped axis) is a blocker.

2.2 Homography check. For one in-place rotation pair, derive the context and target intrinsics from the manifests and independently compute the general pure-rotation homography, K_target times R_target_from_context times inverse(K_context), without assuming the two intrinsics are identical, then warp a pixel grid. If the intrinsics coincide this reduces to the single-K form, but assuming so would blind the test to exactly the resize and crop inconsistencies it exists to catch. The pipeline's correspondences for that pair must agree with the homography within the same 0.1 pixel tolerance as 2.1; bit equality is not required for floating-point camera algebra, and any systematic offset is a blocker. This confirms the depth-free special case end to end on real data.

2.3 One-scene reproduction, the audit's centerpiece. Recompute every Experiment Zero row for one scene (apartment_0) with an independent script whose only permitted inputs are the frozen cached feature arrays, the manifests with cameras and depth, the persisted sample_id values, and, for existing Phase 3 records, the stored realized Random-Patch indices rather than regenerated draws. The independence boundary: a lot function that merely opens a parquet or numpy file may be used; any lot code that transforms coordinates, maps pixels to patches, filters visibility, pools features, constructs masks, or scores is off limits and must be reimplemented from PROTOCOL.md. Geometry, mapping, nulls, pooling, centering, and scoring are all independent implementations. Compare against the shipped parquet row by row on (sample_id, variant, path, metric), agreement within 1e-4 per value; the historical parquet predates sample_id, so match it on the keys it has and note the limitation. When the corrected re-run exists, repeat the row-by-row comparison against it; that comparison is the strongest single piece of evidence the audit produces. Disagreement localizes to whichever module the mutant tests then implicate.

2.4 Aggregate reproduction. First confirm which metric definitions produced the parquet under audit. The pre-correction Phase 3 run used centering and Mean-Feature definitions now known to diverge from PROTOCOL.md, so its aggregates (overall centered margin +0.140, bin margins 0.075 to 0.147, one-patch-off cost 0.088, VGGT margin +0.013, VGGT rotation margin -0.046, path agreement within 0.003) are historical observations, not pass or fail targets. The normative check runs against the corrected re-run parquet: with independent pandas code, recompute every quantitative value currently claimed in the findings and tables, and require exact agreement with the current claims. For the historical parquet, reproduce its aggregates under the definitions its code actually implemented, recoverable from git history, and reproduce the corrected aggregates under the frozen definitions; document that the differences are consistent with the enumerated definition changes (centering, Mean-Feature handling, paired differences, deterministic Random-Patch draws). Do not assign causal attribution of particular movements to particular changes: four definitions changed simultaneously, and attribution requires bridge recomputations that alter one definition at a time. Bridges are cheap in this pipeline, rescoring over cached features, so the validator may run them as an escalation if consistency cannot otherwise be established, but they are not required. Wherever this document elsewhere implies the historical values are targets, this section governs.

2.5 Floors. Recompute the encoder's global mean vector independently and verify the raw Mean-Feature scores. Confirm centered Mean-Feature is absent or marked N/A exactly as frozen, and reject any finite centered Mean-Feature score as a major finding; a finite value there is the signature of the known pre-correction divergence.

2.6 Depth conventions. Re-run the renderer's depth-convention test on raw output and confirm the manifest metadata records the finding and any conversion. For VGGT, independently implement the exact deterministic procedure PROTOCOL.md 4.1 specifies, the secant regression over the first rotation-program frame of every scene with the config-frozen threshold, from the protocol text alone, and compare its classification with the implementation's recorded metadata; separately inspect the VGGT source or documentation for a declared depth convention, which takes precedence if definitive. No region or frame is chosen by inspection. Record the resampling rule used to bring VGGT depth to render resolution; bilinear resampling across depth edges is a major finding per the protocol.

## Part 3: Mutation tests

Copy src/lot into validation/mutants/<mutant_name>/ as a fresh copy per mutant. Each mutant runs in a fresh subprocess with its mutant directory first on PYTHONPATH and no shared Python process with any other mutant, because a cached or path-shadowed import silently tests the original package and makes every kill meaningless. Before the targeted tests execute, the harness records the loaded module path (lot.__file__) and it must resolve inside that mutant's directory; a run without that evidence is void. Then apply one deliberate bug at a time, run the targeted tests, and record kill or survive. A surviving mutant means the test suite would not have caught that bug class; every survivor is a major finding.

Mutation-kill tests, 3.1 through 3.5: the criterion is that an existing or validator-defined correctness test fails under the mutant.

3.1 Swap the relative transform direction (context-from-target). The round-trip and two-plane tests must fail.
3.2 Shift the pixel-to-patch mapping by half a patch. Splat placement tests must fail.
3.3 Disable the z-buffer (last write wins). The occlusion test must fail.
3.4 Unproject with ray distance instead of planar z. Reprojection tests must fail.
3.5 Remove the arccos clamp. An exact identity is useless here: (trace(R) - 1) / 2 equals exactly 1 and arccos is defined, so the mutant survives on clean inputs. The clamp exists for floating-point overshoot, so construct the trigger deterministically: take a near-identity rotation and scale the matrix by (1 + 1e-13), making the arccos argument compute slightly above 1. With the clamp, the result is finite and near zero degrees; without it, the targeted test must catch the NaN. A survivor here means the suite never exercises the overshoot condition the clamp protects against.

Semantic negative controls, 3.6 and 3.7: these are not mutation kills, and no existing test is expected to fail. They deliberately violate a scientific assumption and check that the preregistered pathological signature appears. A failure here means the analysis is unexpectedly insensitive to the violation, and it is reported as its own finding category rather than as a surviving mutant.

3.6 Leak the target, with an unambiguous signature: substitute the actual target feature at the target correspondence into Oracle-Transport's prediction, so on the per-point path the score becomes the cosine of a vector with itself, equal to 1 within numerical tolerance (1e-6) in raw cosine and, wherever defined, in centered cosine. Rerun one scene's Experiment Zero and confirm that signature; record it next to the real numbers. The contrast is the evidence that the shipped results are not quietly leaking. A partial, ambiguous inflation is not a kill.
3.7 Shuffle correspondences within a pair. Equality with Random-Patch is not the criterion: spatially correlated features let a within-scene permutation legitimately beat a uniform random read. The pre-registered kill criterion is that shuffling destroys at least half of the paired Oracle-over-No-Warp-Copy margin, with the degradation statistically clear under scene-level bootstrap, which requires running the shuffle control across the full Phase 3 scene set or a preregistered multi-scene subset; if it is run on a single scene, scene-level bootstrap is meaningless and pair-level uncertainty is used instead. If an exact null is wanted instead, draw the permutation from the same distribution as Random-Patch and require statistical indistinguishability from it. Either way, the check confirms correspondence identity is load-bearing rather than decorative.

## Part 4: Output forensics

4.1 Record accounting. Do not assume the record layout. First establish, from PROTOCOL.md 3.2 and one inspected parquet file, what one record is, whether metric is a row dimension or a column, what one comparison is, and which variants exist on each path, including that centered Mean-Feature is absent by definition. Then derive the expected record count separately for each path at its established grain, for sample-level grains as manifest pairs times valid sample_ids times variants times applicable metrics, and for aggregated grains as pairs times variants times applicable metrics at the aggregate identity, including structural omissions such as Neighbor-Patch border records and the absent centered Mean-Feature; sum across paths, and state the derivation in the report before inspecting the observed counts. The completed run reported 29,196 comparisons and 233,536 records; treat both as observations to be explained, not inputs to the derivation. Account for every observed-minus-expected discrepancy by exact row identity, sample_id, variant, path, and metric where sample identity exists; the historical parquet predates sample_id, so its accounting uses the keys it has, while the corrected re-run must reconcile exactly. Do not presume the previously observed 32-row difference is caused by Neighbor-Patch border omissions; identify the cause.

4.2 Population checks. Verify pair counts per regime against the render program parameters; verify every stored parallax value falls inside its assigned analysis bin when binning is applied; verify every translation-program pair satisfies the program's frozen rotation bound from the manifest and normative config, and translation is exactly zero for rotation-program pairs per the manifests.

4.3 Hygiene. First establish the table's grain from the frozen schema and one inspected file, then assert uniqueness at that grain: for per-point rows a key of (scene_id, context_frame_id, target_frame_id, sample_id, variant, path, metric), extended by alignment level in Phase 4; for pair-aggregated rows, the frozen aggregate identity. Fields below the grain are supposed to repeat, so a duplicate check at a coarser key would flag valid long-format data as duplicates. No nonfinite value is permitted in any score the protocol defines; the only permitted missing metric is centered Mean-Feature, represented either by row absence or by an explicit N/A marker, and the validator confirms exactly one representation is used consistently and records which. Any other NaN or Inf is a major finding. Re-run one scene's evaluation twice and confirm identical output apart from timestamps.

## Part 5: Claim-by-claim verification

Take FINDINGS (or the findings section of the draft) and, for every quantitative sentence, write the single query over the parquet that proves it, run it, and paste the result next to the sentence in the report. Include the scoping claims: run the batch-equality test against the real model on the cluster and confirm it passes rather than skips, and confirm the suite asserts the length-one sequence axis. Any sentence without a passing query is a major finding.

## Report and sign-off

VALIDATION_REPORT.md ends with a verdict: pass, pass with minor findings, or fail, plus the list of blockers and majors. Phase 4 implementation does not start until blockers are resolved and the resolution is itself re-verified by re-running the affected checks. The validator signs off only on what was checked; anything skipped is listed as unverified, not assumed.
